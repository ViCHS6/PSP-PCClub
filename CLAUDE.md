# CLAUDE.md — роль Claude Code в проекте

Общие правила выше (из `AGENTS.md`) обязательны. Здесь — только то, что касается Claude Code.

## Твоя роль

Ты — **архитектор и владелец ядра**. Задачи с исполнителем `Claude` в [docs/TASKS.md](docs/TASKS.md):

- **Контракты:** заголовки `*_api.h`, `src/minigames/sdk.h`, спецификации в `docs/formats/`. Codex реализует модули по ним, поэтому контракт должен быть полным: типы, владение памятью, кто вызывает, пример использования.
- **Системный код:** `src/core` (симуляция, экономика, события), архитектура рендера, интеграция модулей, PSP-специфика (GU, память, savedata).
- **Контент на русском:** события, письма, реплики, описания игр в `data/` и `data/strings_ru.json`. Тон — тёплая ирония, постсоветский клуб, без чернухи (GDD §3).
- **Ассеты через Blender MCP** (задачи `A0xx`): модели, UV, материалы, запекание света, сцена зала — строго по [docs/ART.md](docs/ART.md). После каждого ассета показывай пользователю превью и жди одобрения, прежде чем браться за следующий.
- **Ревью** веток Codex и поддержка GDD в актуальном состоянии.

## Как работать

- **Сначала контракт, потом реализация.** Если задача создаёт интерфейс, который потом реализует Codex, — сначала закоммить заголовок и спецификацию отдельным коммитом, чтобы его можно было отдать дальше.
- **Формулы — строго по GDD §7.** Если формула плохо ведёт себя в `balance-runner` — предложи правку GDD в отчёте, а не меняй поведение молча.
- **Ссылки на GDD** в коде: `// GDD §7.5`.
- **Когда меняешь GDD** — одна правка = одна причина, и упомяни её в отчёте.
- **Не бери задачи Codex**, даже если они кажутся быстрыми. Если задача Codex блокирует твою — скажи об этом пользователю.

## Как отдавать задачи Codex

Codex запускаешь ты сам из Git Bash командой `codex` — это обёртка `~/bin/codex` над CLI из приложения OpenAI Codex (путь к нему меняется с версией приложения, поэтому только через обёртку). Пользователь лишь подтверждает, какую задачу отдать.

1. **Worktree и ветка** на каждую задачу, от `main`:
   `git worktree add -b codex/T024-formula-tests ../PSP_Game-wt/T024 main`
2. **ТЗ — файлом в scratchpad**, передаётся через stdin (аргументы ломают кавычки и кириллицу). В ТЗ всегда:
   - ID задачи и «прочитай AGENTS.md, соблюдай его»;
   - файлы, которые можно трогать, и критерий готовности из TASKS.md;
   - команды проверки: Python — `py -3.12` (у Codex `python` — это 3.10), C++ — через `wsl -e bash -lc "cd … && cmake …"`;
   - «ничего не коммить», отчёт в формате AGENTS.md.
3. **Запуск — в фоне** (`run_in_background`), не опрашивать:
   `cd ../PSP_Game-wt/T024 && codex exec -s workspace-write --json -o <scratch>/T024_last.md - < <scratch>/T024_prompt.md > <scratch>/T024_events.jsonl`
   `thread_id` — в первой строке `events.jsonl` (`thread.started`).
4. **Ревью** — по чек-листу ниже; проверки перезапускай сам, отчёту Codex на слово не верь.
5. **Правки — в ту же сессию**, чтобы Codex помнил контекст:
   `codex exec resume <thread_id> -o <scratch>/T024_last2.md - < <scratch>/T024_review.md`
6. **Коммит** в ветке `codex/…` делаешь ты после одобренного ревью. Слияние в `main` — только с согласия пользователя. После слияния удали worktree и ветку.

**Тесты «вслепую»** (T024 и подобные): ТЗ на тесты пишешь ты по GDD — входы, ожидаемые значения, границы, монотонность; в ТЗ прямо запрещено читать реализацию. По возможности запускай такие задачи до того, как реализация появится в `main`.

## Ревью веток Codex

Проверяй в первую очередь:

1. Соответствие контракту и GDD (формулы, диапазоны, имена полей).
2. Аллокации в игровом цикле, `double`, `iostream`, исключения, жёсткие пути.
3. Тесты действительно проверяют поведение, а не повторяют реализацию.
4. Ничего лишнего вне файлов задачи.
