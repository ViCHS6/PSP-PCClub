## Проект

Homebrew-симулятор владельца компьютерного клуба начала 2000-х для **Sony PSP**. Первое лицо, low-poly 3D, диегетический интерфейс через ОС на ПК администратора. Постсоветский сеттинг, старт игры — 1 сентября 2001.

- **Дизайн:** [GDD.md](GDD.md) — источник истины по механикам, формулам (§7) и схеме данных (§8).
- **Платформа:** [PSP_DEVELOPMENT_REPORT_RU.md](PSP_DEVELOPMENT_REPORT_RU.md) — ограничения PSP, бюджеты, инструменты.
- **Задачи:** [docs/TASKS.md](docs/TASKS.md). Работай только над задачей, которую тебе назначили, по её ID.

Если задача противоречит GDD — не выбирай молча: напиши об этом в отчёте и сделай так, как сказано в задаче.

## Целевое железо

- Устройство тестов — **PSP Go** (накопитель `ef0:`). Совместимость с PSP-1000 обязательна.
- `PSP_LARGE_MEMORY=0`, пиковая RAM ≤ **20 МиБ**, VRAM ≤ **2 МиБ**.
- Цель — стабильные **30 FPS** в худшей сцене.
- Экран 480×272. Весь текст на экране — кириллица, пиксельный bitmap-шрифт.

## Структура репозитория

```
src/core/       симуляция, экономика, события, данные, сохранения — чистый C++, БЕЗ PSP-зависимостей
src/platform/   psp/ и pc/ — ввод, звук, файлы, savedata, время, память (одинаковый интерфейс)
src/render/     GU/GUM (PSP) и SDL2/GL (PC) — сцена, меши, текстуры, 2D-слой, шрифт
src/ui/         ОС администратора: окна, фокус, курсор, программы
src/game/       мир, игрок, взаимодействие, посетители в 3D, мини-игры обслуживания
src/minigames/  играбельные мини-игры (Змейка, Сапёр…) — только через src/minigames/sdk.h
src/tools/      PC-утилиты на C++: balance-runner, minigame-runner (только PC-сборка)
tests/          юнит-тесты (doctest), собираются только в PC-сборке
tools/          Python-инструменты: build_data, конвертеры, генераторы, balance-runner-скрипты
data/           исходники данных: JSON/CSV + strings_ru.json
assets/         исходники графики и звука (OBJ, PNG, WAV/OGG)
docs/           TASKS.md, WORKFLOW.md, форматы файлов (docs/formats/*.md)
build/          артефакты сборки — не коммитить
```

**Файлы-контракты** — заголовки с именем `*_api.h` и `src/minigames/sdk.h`, а также спецификации в `docs/formats/`. Их меняют только задачи, у которых в TASKS.md явно указано «меняет контракт». Если для твоей задачи контракта не хватает — не правь его, а опиши нужное изменение в отчёте.

## Сборка и проверки

> Команды появятся в задаче T001. До неё раздел — план.

```bash
# PC-сборка (симуляция, тесты, отладка мини-игр)
cmake -S . -B build/pc -DTARGET=pc && cmake --build build/pc -j
ctest --test-dir build/pc --output-on-failure

# PSP-сборка (EBOOT.PBP)
psp-cmake -S . -B build/psp -DTARGET=psp && cmake --build build/psp -j

# Данные
python tools/build_data.py data/ -o build/data.pak

# Баланс
build/pc/balance-runner --days 90 --seed 1 --strategy normal --out build/balance.csv
```

**Перед сдачей задачи обязательно:**

1. PC-сборка без предупреждений (`-Wall -Wextra`), все тесты проходят.
2. Если трогал код, который попадает на PSP, — PSP-сборка тоже собирается.
3. Если трогал `data/` — `build_data.py` проходит валидацию.
4. Python-инструменты запускаются на Python 3.11+, зависимости — только стандартная библиотека и Pillow.

Если что-то из этого проверить не удалось (нет тулчейна, нет устройства) — **прямо напиши в отчёте, что не проверено**.

## Правила кода C++

- **C++17**, `-fno-exceptions -fno-rtti`. Без `iostream`, без `std::thread`.
- **Никаких аллокаций в игровом цикле.** Память — при загрузке; в цикле — пулы фиксированного размера и `std::array`. `std::vector` допустим только при загрузке и в tools/tests.
- `float`, не `double`, в коде, который идёт на PSP. Суффикс `f` у литералов.
- Деньги — `int32_t`, рубли. Время симуляции — целые игровые минуты.
- Случайность — только через `core/rng` (xorshift с сидом). Никаких `rand()` и времени системы в `src/core`.
- `src/core` не зависит ни от чего, кроме стандартной библиотеки. Он собирается и в `balance-runner`.
- Пути к файлам — только относительно папки приложения (через `platform`). Нигде не писать `ms0:` или `ef0:`.
- Строки для игрока — только ключи из `data/strings_ru.json`, не литералы в коде.
- Стиль: `snake_case` для функций и переменных, `PascalCase` для типов, `kCamelCase` для констант. Отступ 4 пробела. `#pragma once`.
- Комментарии — на русском, коротко, только там, где «почему» неочевидно. Формулы из GDD помечать ссылкой: `// GDD §7.4`.

## Правила данных

- Исходники: `data/*.json`, `data/*.csv`, `data/events/*.json`. Схема — GDD §8.
- `id` — `snake_case` латиницей, уникальный в своей таблице.
- Все тексты — в `data/strings_ru.json`. Ключ: `<таблица>.<id>.<поле>`, например `ev.license_check.intro`.
- Числа баланса — только в данных, не в коде. В коде допустимы лишь константы из формул GDD (например, показатель степени).
