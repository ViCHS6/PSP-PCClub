# Работа с несколькими агентами

Как разделены задачи между Claude Code и ChatGPT Codex, как их запускать параллельно и как сводить результат. Сами задачи — в [TASKS.md](TASKS.md), общие правила для агентов — в [AGENTS.md](../AGENTS.md).

---

## 1. Принцип разделения

**Claude Code — архитектор и владелец ядра.** Пишет контракты (интерфейсы и форматы), связанные системы, где важно держать в голове весь GDD, и весь игровой текст на русском.

**Codex — исполнитель по спецификации.** Берёт самодостаточные задачи с чётким контрактом и проверяемым результатом: инструменты, конвертеры, тесты, мини-игры, отдельные программы ОС. Такие задачи удобно запускать пачкой параллельно.

**Человек** — устройство (PSP Go), решения по дизайну, вливание веток, приёмка.

### Почему так

Это практическая эвристика, а не жёсткое правило. Обе модели быстро обновляются: если агент стабильно проваливает какой-то тип задач, переназначьте его.

| | Claude Code | Codex |
|---|---|---|
| **Сильные стороны** | Держит в контексте большой дизайн-документ и несколько модулей сразу; аккуратно проектирует интерфейсы и связи систем; хорошо пишет живой текст на русском с нужным тоном; удобен в локальной многошаговой работе (WSL, сборки, отладка) | Сильные результаты на чётко поставленных задачах с проверяемым итогом; облачные задачи можно запускать по несколько штук одновременно; хорош в тестах, скриптах и классических алгоритмах (мини-игры); встроенное ревью кода |
| **Слабые стороны / риски** | Дорогие длинные сессии; склонность сделать «заодно» больше, чем просили — поэтому жёсткие границы файлов в задачах | Облачная песочница — без PSP, без GUI и PPSSPP; хуже, когда спецификация размыта и ответ надо выводить из большого контекста; игровые тексты лучше отдавать Claude |
| **Значит, даём** | Контракты, `core`, события, рендер-архитектура, интеграция, контент и тексты, ревью веток Codex | Инструменты на Python, загрузчики по формату, тесты по GDD, мини-игры по SDK, программы ОС по `ui_api.h`, CI, аудит, ревью веток Claude |

### Перекрёстная проверка

Две разные модели ошибаются по-разному. Этим пользуемся:

- **T024:** тесты формул пишет Codex **по GDD**, не глядя на реализацию Claude (T022). Расхождение — значит, ошибка в одном из двух или неоднозначность в GDD.
- **Ревью:** каждую ветку Claude смотрит Codex, каждую ветку Codex — Claude. Решение о вливании — за вами.

## 2. Порядок работы: «контракт → параллельная реализация»

```
Claude: контракт (заголовок *_api.h + docs/formats/*.md)  ──►  влить в main
                                                                  │
                         ┌────────────────────────────────────────┼──────────────────────┐
                         ▼                                        ▼                      ▼
              Claude: реализация ядра               Codex: инструмент по формату   Codex: тесты по GDD
                         │                                        │                      │
                         └──────────────── перекрёстное ревью ────┴──────────────────────┘
                                                   ▼
                                       Человек: влить, проверить на Go
```

- Контракт вливается в `main` **до** того, как по нему стартуют задачи Codex. Иначе Codex работает по устаревшему интерфейсу.
- Агенты не правят контракты в чужих задачах. Нужна правка — пишут в отчёте, вы заводите задачу на Claude.
- Каждая задача в TASKS.md указывает, какие файлы она трогает. Две одновременные задачи не трогают одни и те же файлы.

## 3. Подготовка (один раз)

1. **Git.** Инициализировать репозиторий, первый коммит с документами.
   ```bash
   git init -b main
   ```
2. **GitHub.** Для облачных задач Codex нужен репозиторий на GitHub — создайте приватный и запушьте `main`.
3. **Окружение Codex в облаке.** В настройках окружения укажите скрипт установки: PC-сборка (`cmake`, `g++`, `libsdl2-dev`, `python3`, `pillow`). PSP-тулчейн в облаке не обязателен: задачи Codex проверяются PC-сборкой, PSP-сборку проверит CI (T005) или вы.
4. **Claude Code.** Запускайте каждую задачу в **отдельном git worktree**, чтобы параллельные сессии не мешали друг другу. В десктоп-приложении это делается при старте сессии; в терминале:
   ```bash
   git worktree add ../PSP_Game-T020 -b claude/T020-core-api
   ```

## 4. Как запускать задачу

### Claude Code

Новая сессия в своём worktree, сообщение:

```
Выполни задачу T020 из docs/TASKS.md.
Сначала прочитай AGENTS.md, CLAUDE.md и разделы GDD, на которые ссылается задача.
Работай только в файлах задачи. В конце — отчёт по шаблону из AGENTS.md.
```

### Codex

Облачная задача (или Codex CLI локально), сообщение:

```
Выполни задачу T021 из docs/TASKS.md. Правила — в AGENTS.md.
Контракт — в файлах, указанных в задаче; не меняй их.
Проверь результат командами из раздела «Сборка и проверки» AGENTS.md.
В конце — отчёт по шаблону из AGENTS.md, включая что не удалось проверить.
```

### Ревью чужой ветки

```
Сделай ревью ветки codex/T021-build-data против docs/TASKS.md (T021), AGENTS.md и GDD §8.
Найди нарушения контракта, правил AGENTS.md и ошибки. Ничего не правь — только список замечаний.
```

## 5. Цикл одной задачи

1. Задача в TASKS.md: все зависимости `done` → можно стартовать, статус `in_progress`.
2. Агент работает в своей ветке, сдаёт отчёт, статус `review`.
3. Ревью другим агентом. Замечания → тот же агент правит в той же ветке.
4. Вы вливаете ветку в `main` (контракты — первыми), статус `done`.
5. Для задач, которые идут на PSP, — проверка на Go хотя бы раз в веху.

**Конфликты в `docs/TASKS.md`:** агенты меняют только статус своей строки, поэтому конфликт — это одна ячейка, решается вручную за секунду.

## 6. Волны параллельной работы

| Волна | Claude | Blender (Claude + MCP) | Codex | Человек |
|---|---|---|---|---|
| 1 | T001, T020 (две сессии) | — | T002, T003, T013 | T004, A001, A002 |
| 2 | T010, T022, T023 | A004 | T005, T011, T021, T024, A012 | — |
| 3 | T026, T030 | A007 | T012, T025, A003, A011 | — |
| 4 | T014, T027, T031, T050 | A005 → A006 | T032, T041, T042, T061 | — |
| 5 | T033, T040 | A008 → A009 | T051, T052 | T015 |
| 6 | T043, T053, T060 | — | — | A010, A013 |
| 7 | T062 | — | — | — |
| 8 | — | — | T063 | T064 (после T063) |

Волна — ориентир, а не расписание: задача стартует, как только её зависимости в статусе `done`.

**Колонка Blender — одна очередь.** Blender MCP управляет одним запущенным Blender, поэтому задачи с MCP идут **строго по одной** (стрелка → означает «друг за другом»). Обычные сессии Claude при этом работают параллельно.

**Сколько агентов одновременно.** Разумно: 1–2 сессии Claude и 2–4 задачи Codex. Больше — и узким местом становитесь вы: ревью и вливание.

## 7. Ассеты

Правила графики — [ART.md](ART.md), задачи — дорожка `A0xx` в [TASKS.md](TASKS.md#дорожка-ассетов-a0xx).

| Кто | Что |
|---|---|
| **Вы** | Арт-директор: утверждаете арт-библию, принимаете каждый ассет по превью, доводите персонажей и анимации, проверяете на Go |
| **Claude Code + Blender MCP** | Модели пропсов и комнаты, UV, материалы, запекание света, сцена зала, черновики персонажей |
| **Codex** | Конвейер: выгрузка из Blender без интерфейса, проверка бюджетов, превью; процедурные 2D-текстуры (экраны, иконки ОС) |

### Почему так

- Blender MCP работает с Blender **на вашем ПК** — облачные задачи Codex до него не дотянутся.
- `.blend` — двоичный файл, git не умеет сливать его правки. У каждого `.blend` один владелец — задача, назначенная на него.
- MCP хорошо справляется с low-poly формами из примитивов (мебель, техника, комната) и плохо — с органикой. Поэтому персонажи — из жёстких частей (ART.md §6), а их доводка и анимации — за вами.
- Codex не может открыть `.blend`, поэтому ревьюит ассеты по превью `assets/previews/` и отчёту `validate_assets.py`.

### Запуск задачи с Blender

1. Запустите Blender, включите аддон MCP, откройте файл задачи (или шаблон).
2. Новая сессия Claude Code, сообщение:
   ```
   Выполни задачу A005 из docs/TASKS.md через Blender MCP.
   Правила — AGENTS.md и docs/ART.md. Начни с копии assets/src/_template.blend.
   Показывай мне превью после каждого ассета. В конце — python tools/assets.py build и отчёт.
   ```
3. Принимайте ассеты по одному, по превью. Замечания — в ту же сессию.

### Git LFS

`.blend` и `.png` хранятся в Git LFS (см. `.gitattributes`). Что нужно знать:

- После клонирования: `git lfs pull`.
- **Облачное окружение Codex:** добавьте `git lfs pull` в скрипт установки, иначе вместо PNG агент увидит текстовые указатели LFS.
- У GitHub ограничен бесплатный объём LFS (хранилище и трафик). Для low-poly ассетов этого хватит надолго, но крупные референсы и рендеры в репозиторий не кладите — `docs/art_refs/` держите лёгким (JPG, ссылки).

## 8. Чего избегать

- Запускать задачу, пока её контракт не влит в `main`.
- Давать двум агентам задачи с пересекающимися файлами.
- Вливать ветку без PC-сборки и тестов.
- Принимать «готово» без отчёта о том, что **не** проверено. Задачи Codex в облаке почти никогда не проверены на PSP — это нормально, но должно быть написано.
- Позволять агенту «заодно» чинить чужой модуль: это новая задача.
- Запускать две задачи с Blender MCP одновременно или давать двум агентам один `.blend`.
