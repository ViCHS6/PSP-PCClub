Разработка игр для Sony PSP

Практический отчёт • Проверка источников: 25 октября 2026 года

Рекомендуемый старт: C или C++, современный PSPDEV/PSPSDK, WSL2 с Ubuntu на Windows, CMake, PPSSPP и настоящая PSP для проверки. Для максимально широкой совместимости проектировать игру под PSP-1000: 32 МБ физической RAM, ориентировочно 24 МиБ обычного пользовательского адресного пространства и базовый бюджет 2 МиБ видеопамяти.

Это исследование инструментов и требований. SDK, драйверы и прошивки на компьютере или консоли не устанавливались; приведённые команды не проверялись запуском в этой среде. Сборка конкретной игры и замеры на устройстве в объём исследования не входят.

1. Какой путь разработки выбрать

1.1. Практический путь — homebrew

Для независимой разработки использовать PSPDEV — открытый комплект инструментов сообщества. В него входят компилятор, библиотеки и инструменты сборки; PSPSDK — его часть с интерфейсами системы PSP, графикой, звуком и примерами. Это отдельный от Sony проект. PSPDEV предусматривает создание приложений как для custom firmware, так и для официальной прошивки с подходящей упаковкой приложения. PSPDEV, состав комплекта.

Основной результат сборки — EBOOT.PBP, который запускается из папки игры. Для отладки сохраняются также ELF с символами и, при использовании PSPLINK, незашифрованный PRX. Не требуется превращать собственную игру в ISO. Руководство по сборке, отладка.

Историческая лицензированная разработка Sony с закрытым SDK, специальным оборудованием и выпуском на UMD — отдельный процесс. Доступность нового договора и выпуска для PSP в 2026 году в рамках исследования не подтверждена. Поэтому его нельзя закладывать как доступный путь старта; отчёт ориентирован на самостоятельное распространение homebrew.

1.2. Прошивка и запуск на устройстве

Для полного цикла разработки с PSPLINK практически удобна PSP, допускающая запуск homebrew и отладочных модулей. Для выпуска на официальной прошивке потребуется отдельно проверить подписанный вариант, используемые API и совместимость с выбранными версиями firmware. Наличие ebootsigner в комплекте само по себе не гарантирует запуск любой программы во всех конфигурациях. Инструменты PSPDEV.

Актуальность руководств: README ARK-4 теперь направляет в ARK-5. ARK-5 направляет за установкой в FasterARK; его текущая инструкция указывает официальные прошивки 6.60/6.61. Старые инструкции PRO/ME/Infinity нельзя автоматически переносить на любую модель. Для уже работающей консоли сначала зафиксировать её модель, прошивку и способ запуска homebrew; менять firmware ради первого прототипа необязательно. ARK-4, ARK-5, FasterARK.

1.3. Решение для первой игры

Моя инженерная рекомендация: однопользовательская игра, поддержка PSP-1000, 2D или компактное 3D, ресурсы с карты памяти, 30 либо 60 кадров/с по результатам прототипа. Это оставляет возможность позже добавить улучшения для моделей с большей памятью. Сетевая игра, собственное использование Media Engine и сложные видеоформаты заметно увеличивают объём платформенной работы.

Состав и назначение компонентов подтверждаются описанием PSPDEV, PSPSDK, схемой toolchain, руководством по редактору и сборке и отладке.

Не скачивать каждый компонент отдельно без необходимости. Установка готового PSPDEV закрывает большую часть таблицы. Полная сборка SDK из исходников нужна для изменения самого toolchain, специальных платформ или воспроизводимости на уровне исходников, а не для первого Hello World.

3.2. Оборудование

Нужны компьютер, носитель для игры и PSP с рабочими кнопками, аналоговым контроллером, питанием и возможностью запуска homebrew. Для обычных моделей использовать кабель mini-USB с передачей данных; у Go — собственный разъём. Для ручного копирования подойдёт USB-режим накопителя или совместимый кардридер. Для PSPLINK нужен именно обмен данными по USB.

Минимально достаточно одной PSP выбранной целевой модели. Если заявляется поддержка всего семейства, разумный тестовый набор — PSP-1000, одна из 2000/3000, Go и Street. Вторую Wi-Fi PSP добавлять, когда начинается разработка ad hoc. Это рекомендация по покрытию, а не требование SDK.

3.3. Версии и воспроизводимость

На дату проверки GitHub API PSPDEV возвращает v20261001 как последний опубликованный обычный release, от 1 октября 2026 года. Среди assets есть pspdev-ubuntu-latest-x86_64.tar.gz, ARM64-сборка Ubuntu и сборки для других систем. Это дата комплекта PSPDEV, а не версия firmware PSP. Релиз v20261001.

Для проекта сохранять release/tag или commit SDK, версию компилятора, список библиотек и параметры сборки. Для Docker фиксировать digest образа либо конкретный tag после проверки. latest удобен для знакомства, но не фиксирует неизменное окружение. Docker PSPDEV, образы и теги.

Не строить план вокруг предполагаемой кнопки экспорта из современного Unity, Unreal или Godot. Если выбран конкретный неофициальный порт такого движка, сначала подтвердить его работоспособность, сборку и производительность. Проверенная в этом отчёте основа — PSPDEV и нативный код.

5. Настройка среды на Windows и первая сборка

5.1. Основной вариант — WSL2 + Ubuntu

  1. Установить WSL с Ubuntu по инструкции PSPDEV; wsl --install выполняется в PowerShell с правами администратора, после чего может понадобиться перезагрузка.
  2. Установить зависимости и распаковать готовый PSPDEV для соответствующих Ubuntu и архитектуры. Не смешивать x86-64/ARM64 или архивы для разных ОС.
  3. Задать в shell переменную PSPDEV и добавить $PSPDEV/bin в PATH.
  4. Проверить psp-config --pspdev-path и psp-gcc --version.

Пример переменных внутри Ubuntu, если SDK распакован в ~/pspdev:

export PSPDEV="$HOME/pspdev"
export PATH="$PSPDEV/bin:$PATH"
psp-config --pspdev-path
psp-gcc --version

Инструкция с актуальным перечнем системных пакетов и архивов: PSPDEV для Windows. Linux и macOS также поддерживаются; WSL нужен именно для Windows-сценария.

Особенность текущей рабочей папки: E:\ai tests\PSP_Game содержит пробел. PSPDEV требует, чтобы путь установки SDK был абсолютным, без пробелов и специальных символов. SDK лучше разместить в ~/pspdev, а рабочую Linux-сборку — например, в ~/src/psp_game. Исходники в имеющейся папке можно сохранить; существующие файлы переносить ради отчёта не требуется. Сборку непосредственно из пути с пробелом надо отдельно проверить: часть старых Makefile может его обрабатывать неверно. Требования к пути PSPDEV.

5.2. Альтернатива — Docker

Образ pspdev/pspdev содержит подготовленную среду сборки. Для Windows нужен Docker, умеющий запускать Linux-контейнеры. Пример ниже показывает, как корректно передать существующий путь с пробелом в PowerShell; он предполагает, что в папке уже есть Makefile проекта:

docker run --rm --mount "type=bind,source=E:\ai tests\PSP_Game,target=/source" -w /source pspdev/pspdev:v20261001 make

Внутри контейнера путь будет /source. Доступ Docker к диску E: зависит от настроек компьютера. Перед сборкой следует проверить монтирование; не добавлять привилегированный режим без конкретной необходимости. Docker решает сборку, но USB-отладку на физической PSP нужно настраивать отдельно. Docker-инструкция PSPDEV.

5.3. Первая проверка среды

В пустой папке проекта создать main.c и CMakeLists.txt по официальному Hello World PSPDEV. Затем в Ubuntu:

psp-cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build

Ожидаемый результат — EBOOT.PBP в каталоге сборки. Сохранить рядом ELF с символами. Затем проверить пакет в PPSSPP и на устройстве:

<корень накопителя>/
└── PSP/
    └── GAME/
        └── MyGame/
            ├── EBOOT.PBP
            └── data/

Необходимо копировать и данные, которые ожидает программа. На PSP Go проверить внутренний накопитель отдельно. Для игровых ресурсов использовать путь запуска приложения или относительные пути, а не единственную жёстко заданную строку ms0:.

После Hello World последовательность проверки: ввод → спрайт или треугольник → звук → чтение ресурса → сохранение → выход через HOME → suspend/resume. Базовые примеры PSPSDK.

6. Ограничения CPU, памяти и графики

В этом разделе аппаратные ограничения отделены от рекомендаций проекта. Частоты, объём установленной памяти и поддерживаемые форматы — свойства платформы; количество врагов, полигонов или эффектов — результат конкретной реализации и замеров.

6.1. CPU и вычисления

Свойство Ограничение и следствие
Основной CPU 32-битный MIPS-производный Allegrex, little-endian; обычный код ПК надо перекомпилировать и проверить предположения о данных
Частота Штатный диапазон до 333 МГц; часто встречаются режимы 222 и 333 МГц. Частоту тестирования фиксировать
Параллелизм Потоки игры делят основной CPU. Нельзя рассчитывать на несколько обычных CPU-ядер как на современном ПК
FPU Аппаратно поддерживается одинарная точность float; double существенно дороже
VFPU Полезен для векторов и матриц, но имеет особенности точности и требует корректной работы с контекстом потока
Media Engine Второй специализированный процессор существует, но не является готовым дополнительным ядром для обычных игровых потоков
Кэш и GPU GPU не видит грязные строки CPU-кэша; нужны корректная запись в память, синхронизация и время жизни буферов
Управление памятью Нет обычной MMU; нельзя рассчитывать на настольную модель виртуальной памяти и подкачку вместо бюджета RAM

Источники: Allegrex — разработчики PPSSPP, практические замечания по PSP, исследование VFPU.

Практически: использовать литералы 1.0f, функции вроде sinf/sqrtf, включить -Wdouble-promotion и -Wfloat-conversion. Физику, поиск пути и распаковку измерять на PSP. Сначала упрощать алгоритм и объём работы, затем оптимизировать горячие участки. Полезны пулы объектов и отсутствие неконтролируемых выделений памяти в кадре.

Для совместимости не требовать разгона выше штатных 333 МГц. Наличие функции overclock в современных CFW не делает её базовой характеристикой консоли. Работа на 333 МГц также увеличивает расход батареи. CPU PPSSPP, возможности ARK-5.

6.2. RAM: объём консоли и память игры — разные величины

32 МБ PSP-1000 не равны 32 МБ свободного malloc. В обычной схеме пользовательская область начинается с 0x08800000, а 32-МиБ RAM заканчивается на 0x0A000000: разница — 24 МиБ. Код, статические данные, библиотеки, стеки и служебные выделения тоже расходуют эту область. Это ориентир адресного пространства, а не обещание свободного heap после загрузки. Карта памяти в PPSSPP.

Для 64-МБ моделей разность между концом RAM 0x0C000000 и той же базой пользователя даёт 56 МиБ. Это верхняя оценка адресного диапазона при его расширении, а не гарантированный размер пользовательского раздела или свободного heap. Реальное распределение зависит от загрузчика, firmware, метаданных приложения и версии сборочной системы. Нужна проверка и режима старта, и фактического выделения памяти; единого гарантированного числа свободных мегабайт нет.

Изменение в современном PSPSDK: текущий build.mak для целевой firmware выше 3.90 использует политику расширенной памяти по умолчанию и допускает явное отключение через PSP_LARGE_MEMORY=0. Старое правило «всегда поставить PSP_LARGE_MEMORY=1» уже не универсально. Это описание конкретного Makefile; поведение CMake и загрузчиков необходимо сверять отдельно. Исходник build.mak.

Для совместимого с PSP-1000 проекта дополнительные RAM и специальные области памяти считать необязательными улучшениями. Настройка PSP_HEAP_SIZE_KB управляет запросом heap, но не создаёт физическую память. Параметры runtime.

В диагностике учитывать текущий и максимальный расход собственных аллокаторов, свободное место внутри heap и размер доступного непрерывного блока. Суммарная свободная память не исключает отказ из-за фрагментации. Системные функции измеряют свои области, а не обязательно свободную память malloc; в частности, PSPSDK отдельно описывает pspSdkTotalFreeUserMemSize. Менеджер памяти, пояснение к пользовательской памяти.

6.3. VRAM и экранные буферы

Совместимый базовый бюджет — 2 МиБ графической eDRAM. Исторические спецификации Sony указывают 4 МБ eDRAM суммарно; эту цифру нельзя автоматически записывать как доступную игре VRAM на PSP-1000. Актуальный API содержит sceGeEdramSetSize с вариантами 2/4 МиБ и прямо указывает, что 4 МиБ не принимаются на Fat. Расширение на остальных конфигурациях нужно проверять; базовый рендерер лучше проектировать на 2 МиБ. API GE, первоначальная спецификация Sony.

Ниже — расчёт, а не измерение. Приняты распространённые stride 512 пикселей и высота 272. Видимая ширина экрана — 480; stride означает шаг между строками буфера.

Два framebuffer, 16 бит 544 КиБ 1 504 КиБ
Два framebuffer 16 бит + depth 16 бит 816 КиБ 1 232 КиБ
Два framebuffer 32 бита + depth 16 бит 1 360 КиБ 688 КиБ

Оставшийся объём делят текстуры и дополнительные render targets с учётом выравнивания. Для 2D можно отказаться от depth, если он не нужен. Не следует выделять VRAM как будто экранные буферы бесплатны. Текстуры допускаются и в основной RAM; выгодное размещение зависит от доступа и сцены. GU, размещение текстур и буферов.

Источники: устройство GE, аппаратная схема из исследовательской документации, матрицы костей GE в PSPSDK. Восемь матриц — предел конкретного аппаратного набора, а не общий предел костей персонажа во всей игре.

Следствия для визуального стиля — инженерные рекомендации: запекать сложное освещение; ограничивать прозрачные слои, частицы и полноэкранные эффекты; группировать геометрию по материалам; применять culling и LOD. Современные PBR-материалы, normal mapping и постобработка потребуют собственной адаптации; их стоимость нельзя оценивать по версии игры на ПК.

6.5. Текстуры и форматы

У стандартного sceGuTexImage ширина и высота — степени двойки в диапазоне 1–512, не обязательно одинаковые: например, 128 × 256. Текстура 480 × 272 как единое стандартное изображение требует иной упаковки, обычно контейнера 512 × 512 либо разбиения. Адрес данных должен быть выровнен на 16 байт; layout, stride и swizzle должны соответствовать настройкам GPU. Проверки sceGuTexImage.

Расход квадратной текстуры, расчёт без mipmaps и служебных данных:

Размер RGBA8888, 32 бита 16-битный цвет Индексная T8 Индексная T4
128 × 128 64 КиБ 32 КиБ 16 КиБ 8 КиБ
256 × 256 256 КиБ 128 КиБ 64 КиБ 32 КиБ
512 × 512 1 024 КиБ 512 КиБ 256 КиБ 128 КиБ

У индексных форматов дополнительно хранится палитра CLUT. Для полной цепочки квадратных mipmaps ориентир — ещё около трети памяти. PNG/JPEG — форматы хранения: маленький сжатый файл не означает маленькую текстуру после декодирования. Две 512 × 512 RGBA8888 уже занимают весь базовый объём VRAM без framebuffer.

Рекомендация: начинать с 64–256 пикселей на сторону, 16-битного или палитрового формата, заранее готовить swizzle и атласы до 512 × 512. DXT поддерживается платформой, но может проигрывать по скорости; выбирать после замера. Форматы GU, замечания PPSSPP по памяти и DXT.

6.6. FPS и сложность сцены

Для цели 60 кадров/с бюджет кадра около 16,7 мс, для 30 — 33,3 мс. Это расчёт 1000 / FPS; CPU и GPU могут работать с перекрытием, поэтому отдельно измерять их занятость и ожидания синхронизации.

Универсального полезного лимита «N полигонов», «N draw calls» или «N врагов» нет. Результат меняется из-за формата вершин, прозрачности, размера полигонов на экране, света, материалов, CPU-логики и чтения данных. Бюджет получить на стрессовой сцене конкретной игры. Пиковые рекламные показатели консоли не являются бюджетом реального кадра.

7. Звук, управление, накопитель и сеть

7.1. Звук и видео

В базовом sceAudio доступно 8 аппаратных каналов, mono/stereo PCM; длина буфера должна удовлетворять требованиям API, включая кратность 64 отсчётам. Это не предел в восемь звуков игры: программный mixer может смешать больше голосов, расходуя CPU. PSPSDK Audio.

Для начала выбрать один проверенный выходной режим, например 44,1 кГц, 16-битное stereo, и ограничить число одновременно декодируемых потоков. Расчёт: PCM такого формата занимает 44 100 × 2 × 2 = 176 400 байт/с, около 10,1 МиБ за минуту. Поэтому длинную музыку лучше стримить, а короткие эффекты держать в памяти. Сжатие экономит носитель, но требует decoder buffers и времени CPU.

На Street проверять монофонический динамик, а на всех целевых моделях — наушники, паузу и возобновление аудио. Видео и аппаратные декодеры PSP — отдельная интеграция: наличие поддержки H.264 у консоли не означает, что произвольный MP4 автоматически воспроизводится из игры. Формат, контейнер, API и сценарий streaming проверить отдельным примером. На раннем этапе разумнее обойтись без видео. Спецификация Street, оговорки PPSSPP о Media Engine.

7.2. Управление и интерфейс

Базовое управление: D-pad, один аналоговый контроллер, четыре лицевые кнопки, L/R, Start/Select. Нативного второго стика, L2/R2 и сенсорного экрана в качестве общей базы PSP нет. В современных заголовках SDK встречаются поля правого стика для Go с внешним контроллером, Vita, модификаций и эмуляции; они не означают второй стик на обычной PSP. Структура ввода PSPSDK, физические органы управления Sony.

Рекомендации: dead zone для аналогового ввода, переназначение основных действий, камера без обязательного второго стика, крупные надписи с проверкой кириллицы. HOME и системные кнопки не занимать критическими игровыми действиями. Предусмотреть корректный системный выход, обработку потери фокуса и возвращение из сна. Базовый callback выхода показан в Hello World PSPDEV.

7.3. Носители, загрузки и сохранения

Для homebrew распространять папку игры с EBOOT.PBP и ресурсами. UMD — носитель только для чтения; его ёмкость не ограничивает размер игры, распространяемой с карты. Go обходится без UMD и имеет собственную внутреннюю flash. Sony о Go.

Инженерные требования к I/O:

  • не делать множество мелких синхронных чтений в основном цикле;
  • использовать пакетирование, предзагрузку или ограниченные фоновые задачи;
  • отдельно измерять скорость реальной карты и адаптера: USB 2.0 в спецификации не задаёт скорость чтения ресурсов игрой;
  • обрабатывать отсутствие файла, полный носитель, отказ записи и повреждённое сохранение;
  • сохранять версию формата и проверку целостности; по возможности писать во временный файл с последующей заменой;
  • после suspend/resume проверять состояние потоков, аудио и файлов; не рассчитывать, что открытый ресурс всегда остался доступен.

Предел одного файла и совместимость больших карт зависят от файловой системы, firmware и носителя. Например, FAT32 ограничивает один файл величиной менее 4 ГиБ; это ограничение формата носителя, а не бюджет RAM PSP. Для первой игры разумнее использовать существенно меньшие архивы и проверить выбранный носитель целиком. Microsoft: сравнение файловых систем.

7.4. Сеть

У Wi-Fi моделей используется IEEE 802.11b, инфраструктурный режим через точку доступа и ad hoc. Street не имеет Wi-Fi. Bluetooth Go не является общей сетевой возможностью семейства. Sony о PSP-2000, Sony о Go, PlayStation о Street.

Штатная инструкция PSP перечисляет WEP и WPA-PSK TKIP/AES; обычную современную точку WPA2/WPA3 нельзя считать совместимой без проверки. При необходимости выделять отдельную совместимую тестовую сеть, сохраняя защиту основной сети. Настройки безопасности PSP — Sony.

Для собственного online-сервиса потребуются сервер, проверенные версии TLS/библиотек, таймауты, восстановление соединения и отдельное тестирование. Наличие сетевой библиотеки не гарантирует совместимость современного сервиса. Ad hoc не равен автоматически готовому интернет-мультиплееру. Для всей линейки сделать offline-режим; для сетевой игры публиковать отдельный список поддерживаемых моделей.

7.5. Питание и жизненный цикл

Игра должна корректно переживать сон и пробуждение, системный выход и длительную работу. Не использовать busy-wait для ожидания кадра; временно неактивные потоки должны освобождать CPU. В тестах фиксировать питание от батареи или сети, яркость, частоты и состояние WLAN — это влияет на повторяемость. Конкретное время автономной работы нельзя обещать по паспортным данным старой батареи. Частота и энергопотребление CPU, энергосбережение WLAN — Sony.

9. Отладка и измерение производительности

9.1. PPSSPP — быстрый цикл проверки

Использовать актуальный PPSSPP, держать ELF с символами рядом с EBOOT.PBP или PRX: отладчик может читать из него имена и строки исходников. Для базовой проверки выбрать родное разрешение 1×, выключить улучшения текстур и frame skip, зафиксировать модель/память и частоту эмулируемой PSP. Рекомендации разработчикам homebrew, developer tools.

Ограничение достоверности: PPSSPP не воспроизводит CPU-кэши как настоящая PSP, системные API в значительной мере моделируются; различаются отдельные аспекты звука, цветов и шрифтов. Поэтому ошибки cache writeback, последовательности вызовов и timing могут проявиться только на устройстве. FPS в эмуляторе не является доказательством того же FPS на PSP. Известные отличия.

9.2. PSPLINK и GDB на устройстве

На PSP запускается PSPLINK; на компьютере работают usbhostfs_pc и pspsh. Приложение для этой схемы собирается как незашифрованный PRX, например с BUILD_PRX=1; символы сохраняются в соответствующем ELF. PSPLINK позволяет запускать его с компьютера, получать диагностику и подключать psp-gdb. Для crash-адреса используется psp-addr2line с ELF той же сборки. Порядок отладки PSPDEV.

На Windows для PSPLINK нужны USB-драйвер и отдельная настройка; руководство PSPDEV указывает Zadig и PSP Type B. Для доступа из WSL также используется usbipd-win. USB mass storage и интерфейс PSPLINK — разные режимы: не следует менять драйвер произвольного накопителя. Точный порядок сверять с инструкцией Windows/WSL.

9.3. Что измерять

Встроить в игру компактный debug overlay или лог:

  • время кадра и максимальные задержки на стрессовых участках;
  • CPU update, подготовку рендеринга, ожидание GPU/VBlank и I/O;
  • текущую и пиковую RAM/VRAM, свободное место heap и отказы выделения;
  • число видимых объектов, вызовов отрисовки, вершин/треугольников;
  • число аудиоголосов и случаи нехватки аудиоданных;
  • время старта, загрузки уровня и сохранения.

CPU-профилирование доступно через psp-gprof: для инструментированной сборки используются -pg и -g. Профайлер меняет нагрузку, поэтому окончательное время кадра перепроверять в обычной релизной сборке. Профилирование PSPDEV.

10. Процесс разработки и проверка релиза

10.1. Последовательность работ

  1. Зафиксировать платформу: модели, firmware/loader, C или C++, GU либо SDL, разрешение, 30/60 FPS, носитель, необходимость сети.
  2. Проверить сборку: Hello World → EBOOT → PPSSPP → реальная PSP; сохранить версии окружения.
  3. Собрать технический прототип: ввод, рендеринг, звук, загрузка ресурса, сохранение, выход и сон.
  4. Сделать стрессовую сцену: максимальная планируемая сложность, прозрачность, музыка и одновременное чтение данных.
  5. Установить реальные бюджеты: качество, память, геометрию и лимиты объектов по результатам замеров.
  6. Автоматизировать подготовку ресурсов: проверять размер и формат до попадания данных на консоль.
  7. Создать небольшой законченный фрагмент игры: начало, игровой цикл, победа/поражение и сохранение. Только после этого наращивать контент.
  8. Проверить релиз отдельно от отладки: чистая папка установки, release-сборка, реальные ресурсы и заявленная матрица устройств.

11. Типичные ошибки и открытые решения

Ошибочное предположение Корректное решение
«У PSP 64 МБ, можно занять их все» Задать минимальную модель, режим памяти и измерить фактический бюджет приложения
«4 МБ eDRAM в спецификации — это 4 МБ VRAM для любой PSP» Базово считать 2 МиБ; расширение проверять через API и на нужной модели
«В PPSSPP работает — на PSP тоже будет» Рано включить аппаратные тесты, особенно cache/DMA, audio и suspend
«Маленький PNG почти не расходует память» Считать декодированную текстуру, временный буфер и возможную вторую копию
«Есть восемь аудиоканалов — значит максимум восемь звуков» Различать аппаратный вывод и программный микшер
«Для графики достаточно уложиться в число полигонов» Измерять весь кадр, overdraw, state changes, материалы и CPU
«Восемь bone matrices означают максимум восемь костей персонажа» Разбивать mesh по палитрам костей и учитывать стоимость дополнительных batches
«Код на double дешевле оптимизации» На горячих участках использовать float, проверять компиляторные предупреждения
«На всех моделях есть сеть» Street работает без Wi-Fi; сеть и Bluetooth объявлять отдельными возможностями
«Любой современный роутер и HTTPS подойдут» Проверить точку доступа, криптографические протоколы и конкретный сервер
«PSP-2000+ обязательно существенно быстрее CPU» Большее количество RAM не даёт пропорционального ускорения основного процессора

До начала полноценной игры остаётся выбрать жанр и 2D/3D, минимальную модель, целевой FPS, способ запуска, необходимость сети и видео. Эти решения определяют архитектуру сильнее, чем выбор редактора кода. При отсутствии дополнительных требований рабочая исходная конфигурация — C++ + PSPSDK GU/GUM, WSL2, CMake, PPSSPP, PSP-1000, offline, бюджет около 20 МиБ RAM и 2 МиБ VRAM с последующей проверкой замерами.
